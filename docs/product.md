# Sarjy — Product Specification

## 1. One-paragraph definition

A single-screen web app. The user taps once and then simply talks, like a phone call. Sarjy
understands Egyptian Arabic and English — including both mixed inside one sentence — and
replies out loud in the matching language, in natural dialect (Egyptian or Gulf persona,
switchable). It remembers durable facts about the user across sessions, and it can act:
check weather, look up Islamic prayer times, and create/list appointment bookings —
including resolving culturally-anchored times like "بكرة بعد العصر" (tomorrow after Asr)
into real clock times via the prayer-times API before booking.

## 2. Assignment requirements → product features

| Requirement (from the Sarj brief) | Feature that satisfies it                                                                           |
| --------------------------------- | --------------------------------------------------------------------------------------------------- |
| Listens and responds by voice     | Streaming voice pipeline over one WebSocket                                                         |
| Remembers things across sessions  | `facts` table + automatic background fact extraction                                                |
| ≥1 external API, justified        | Aladhan prayer times (primary justification) + Open-Meteo weather                                   |
| Deployed, accessible via web      | Vercel (frontend) + Cloud Run (backend)                                                             |
| One deep dive, done deeply        | Bilingual: code-switching, language policy, personas, cross-language memory, measured STT benchmark |

## 3. The deep dive: bilingual, concretely

1. **Code-switching input**: Deepgram Nova-3 multilingual mode transcribes mixed
   Arabic/English utterances ("عايز أعمل book لميتنج بكرة").
2. **Language policy** (see §6) governing what language/dialect Sarjy replies in.
3. **Personas as configuration** (see §7): Egyptian 🇪🇬 and Gulf 🇸🇦, each = system-prompt
   style guide + Arabic voice ID + display name. Nothing else.
4. **Cross-language memory**: facts stored in canonical English form regardless of input
   language, so a fact told in Arabic is recallable in English and vice versa.
5. **Benchmark** (`eval/`): ~30 self-recorded utterances (10 Arabic, 10 English,
   10 code-switched; some noisy/fast) run through Deepgram Nova-3, browser Web Speech API,
   and Gemini audio transcription; Word Error Rate per group via `jiwer`; results table
   in `eval/results.md`.
6. **Mixed-direction UI**: correct right-to-left/left-to-right rendering in one transcript.

## 4. UX specification (single screen, no navigation)

- **Visual identity**: Arabic-futuristic. Near-black canvas, one warm accent (amber/gold
  family), Arabic-first typography (Cairo or IBM Plex Sans Arabic from Google Fonts),
  generous space. Bilingual microcopy ("اضغط للكلام · Tap to talk").
- **Centerpiece — the orb**: animated state indicator. Idle = slow breathing; listening =
  ripples driven by real microphone level; thinking = pulse; speaking = waveform. The orb IS
  the status display; no status text needed.
- **Interaction model — call-style**: one tap opens the session; thereafter hands-free.
  Endpointing detects turn ends. User can interrupt Sarjy by speaking (barge-in). Mute
  button always visible. Session auto-ends after ~60s of silence (saves quota).
- **Transcript**: live captions under the orb. Interim words rendered dimmed, solidify on
  final. Each bubble shows a small language badge: `ar` / `en` / `mixed`. Arabic bubbles
  right-to-left, English left-to-right, mixed handled with Unicode direction isolation.
- **Top bar**: Sarjy wordmark · persona toggle 🇪🇬/🇸🇦 · connection dot.
- **"What I remember about you" drawer**: live view of the user's rows in `facts`,
  with a delete button per fact (transparency + easy demo).
- **Bookings panel**: small list of the user's bookings proving they are real database rows.
- **Designed states**: microphone-permission request, reconnecting, and a friendly
  bilingual message when a free-tier rate limit trips (with auto-retry).

## 5. First-use onboarding (no login)

Identity = a UUID generated by the frontend on first visit, stored in localStorage, sent on
every WebSocket connect. On connect the backend checks `facts` for key `name`:

- **Missing** → Sarjy speaks first: "أهلاً! أنا سرجي — اسمك ايه؟ Hi, I'm Sarjy — what's
  your name?" The reply seeds both the `name` fact (via the normal extractor) and the
  mirror-language preference. Not a gate: if the user asks something else, just answer it.
- **Present** → personalized returning greeting: "أهلاً بيك تاني يا {name}!"
  Stated limitation (for writeup): memory is per-browser; real accounts are the production path.

## 6. Language policy (locked rules)

1. **Mirror by default**: reply in the language of the user's last utterance. For mixed
   utterances, reply in the dominant language (majority of characters).
2. **Explicit switches win and stick**: "كلمني عربي" / "speak English" sets
   `users.preferred_language` until changed.
3. **Dialect, never MSA**: Arabic replies follow the active persona's dialect. No Modern
   Standard Arabic, no newscaster tone.
4. **Borrowed words**: in Arabic replies, everyday borrowed English words are written in
   Arabic script ("ميتنج" not "meeting") so the Arabic voice pronounces them naturally.
5. **Detection**: language label per utterance computed from Arabic-script character ratio
   (thresholds: >70% Arabic → `ar`; <30% → `en`; else `mixed`).

## 7. Personas (configuration objects only)

```
egyptian: { style guide: casual Egyptian dialect, warm, lightly witty; voice: <AR voice A>; name: "سرجي 🇪🇬" }
gulf:     { style guide: warm-formal Gulf (Saudi) dialect;             voice: <AR voice B>; name: "سرجي 🇸🇦" }
```

English replies use one shared English voice regardless of persona. Egyptian is the default
and primary demo persona. Gulf output is verified by the user (10 years in Saudi Arabia).

## 8. Tools (function calling — direct, not MCP)

| Tool               | Input                         | Behavior                                                     |
| ------------------ | ----------------------------- | ------------------------------------------------------------ |
| `get_weather`      | city or lat/lon, day          | Open-Meteo forecast; returns compact summary for speech      |
| `get_prayer_times` | city, date                    | Aladhan timings; returns the five prayer times               |
| `create_booking`   | service, datetime ISO, notes? | Insert row into `bookings`; confirm with resolved local time |
| `list_bookings`    | —                             | User's upcoming bookings, soonest first                      |

Anchor behavior: when the user gives a prayer-anchored time ("بعد العصر"), the brain must
call `get_prayer_times` first, resolve to a clock time, then call `create_booking`.
Default city: user's `home_city` fact if present, else Alexandria, Egypt.

## 9. Memory

After each completed exchange, a background task sends the exchange to Gemini with a strict
JSON-only prompt: extract durable personal facts as `[{key, value}]`, keys in canonical
English snake_case (`name`, `favorite_color`, `home_city`, `doctor_name`...). Upsert into
`facts` (unique on user_id+key), recording `source_language`. All current facts are injected
into every system prompt. Ephemeral info (today's mood, current question) must NOT be stored.

## 10. Data model (six tables)

- `users` — id UUID PK · created_at · preferred_persona (default 'egyptian') · preferred_language (nullable)
- `sessions` — id UUID PK · user_id FK · started_at · ended_at (nullable)
- `messages` — id PK · session_id FK · role ('user'|'assistant') · content · language ('ar'|'en'|'mixed') · created_at
- `facts` — id PK · user_id FK · key · value · source_language · updated_at · UNIQUE(user_id, key)
- `bookings` — id PK · user_id FK · service · scheduled_at · notes (nullable) · status ('confirmed'|'cancelled') · created_at
- `turn_metrics` — id PK · message_id FK · speech_recognition_ms · brain_first_token_ms · voice_first_audio_ms · total_ms · created_at

## 11. Echo / self-hearing defense (call-style requirement)

1. Request the microphone with `echoCancellation: true` (plus noiseSuppression).
2. While Sarjy is speaking, a barge-in triggers only on an interim transcript containing
   ≥2 real words — coughs and echo residue must not cut playback.
3. Demo hygiene: moderate speaker volume (documented, not coded).

## 12. Non-goals (do not build)

- No authentication/accounts. No multi-user collaboration.
- No multistep workflow engine (different deep dive) — booking is a single tool call.
- No production-scale infra, queues, or observability stacks.
- No UI beyond the single screen; UI polish is timeboxed (it is not the deep dive).
- No paid tiers of any provider.

## 13. Acceptance narrative (the demo script that must work end-to-end, deployed)

1. First visit: Sarjy greets and asks the name; user answers in Arabic; name is stored.
2. English: "What's the weather like tomorrow?" → correct spoken English answer (tool call).
3. Mid-conversation switch, code-switched Arabic: "احجزلي ميعاد عند الدكتور بكرة بعد العصر"
   → prayer-time lookup → booking row created → Egyptian-dialect spoken confirmation with
   the resolved time; row visible in the bookings panel.
4. Close the tab. Reopen. Personalized greeting by name. Ask in English: "What's my favorite
   color?" (told earlier in Arabic) → correct answer. Cross-language, cross-session memory.
5. Interrupt Sarjy mid-reply and redirect — playback stops instantly, new question answered.
6. Toggle to Gulf persona; user speaks Gulf-accented Arabic; Sarjy replies in Gulf dialect.
